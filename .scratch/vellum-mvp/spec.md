# Spec: Vellum —— 个人据点站（M0–M4）

Status: ready-for-agent

## Problem Statement

站主是一名在俄罗斯的中国留学生。生活里有三件反复发生、但目前没有合适落点的事：

1. **生活费心算**。每月有一笔固定的生活费（卢布），需要随时知道「这个月还剩多少能花」「今天大概能花多少」。目前靠脑内估算和银行 App 的流水回溯，既不准也不及时，房租水电这类月初就已知的大额固定支出会让心算彻底失真。
2. **菜谱散落**。喜欢的菜谱分散在聊天记录、网页截图、视频收藏里，做饭前找不到，做完也没有地方记「这道菜做过几次、大概花多少钱、上次是什么时候做的」。
3. **重要照片被淹没**。手机相册里几万张照片，真正想反复回看的只有几百张。它们没有被组织成「历程」，只是按时间堆着。

市面上每一件事都有成熟产品，但它们都是别人的：数据在别人的服务器上，界面是大众审美，功能是为所有人设计的。站主想要的不是三个工具，而是**一个属于自己的地方**——像家，或者像一本手账。它的主题、语气、外观、功能，全部按自己的喜好来。

同时，站主是分布式系统方向的学生，希望这个项目在工程上是**干净、简洁、好维护**的，并且借它扎实地学会两件事：**正确使用 Postgres**，以及**一套完整的 CI/CD 工作流**。这两个学习目标必须服务于「这个站我每天都会用」这个第一目标，而不是相反。

## Solution

**Vellum** —— 一个单用户、自托管、公网可达的个人网站，主题为「日式异世界旅人的据点」。

站主登录后进入「据点主页」，页面同时是导航和今日状态面板：今天还能花多少钱、最近的一段回忆、一道可以做的菜。从这里进入三个彼此独立的模块：

- **理财**：设定月生活费预算，记录每一笔开销，实时得到「本月剩余」和「今天可用」。用不完的钱月末自动进入「存款」，大额开销从存款支出而不污染月度预算。
- **菜谱**：每道菜有名字、成品照片、结构化食材列表、自由书写的步骤、做过几次、上次做于、成本估算和标签。
- **相册**：以「事件」为一级单位的编年史——一次旅行、一个学期、一件记得住的事。事件有标题、日期区间和一段文字，照片附属其下，每张可以写一句话。

技术上是一个 Go 单体二进制（内嵌 React SPA）+ Postgres，跑在一台海外 VM 的 docker compose 里，`git push` 到 `main` 即自动测试、构建、部署。前端是 PWA，可以添加到手机主屏，在餐厅和超市随手记账。

## User Stories

### 认证与访问

1. 作为站主，我想用用户名和密码登录，以便只有我能访问站内的全部内容。
2. 作为站主，我想在登录后保持登录状态约 30 天，以便日常使用时不必反复输入密码。
3. 作为站主，我想主动登出，以便在借用他人设备后终止会话。
4. 作为站主，我想让所有未登录的请求都被拒绝并跳转到登录页，以便我的开销记录和私人照片不会被公网上的陌生人看到。
5. 作为站主，我想让连续多次失败的登录尝试被暂时锁定，以便公网上的自动化爆破无法穷举我的密码。
6. 作为站主，我想修改自己的密码，以便在怀疑泄露时可以自救。
7. 作为站主，我想把这个站添加到手机主屏并以全屏方式打开，以便它用起来像一个 App 而不是一个书签。
8. 作为站主，我想在手机上流畅地使用所有功能，以便我能在餐厅、超市、路上随手记录。

### 据点主页

9. 作为站主，我想在主页看到通往三个模块的入口，以便一眼就知道能做什么。
10. 作为站主，我想在主页看到「今天还能花多少钱」，以便在决定要不要买某样东西时立刻有依据。
11. 作为站主，我想在主页看到本月剩余预算和存款余额，以便掌握整体财务状态。
12. 作为站主，我想在主页看到最近一段回忆的封面和标题，以便每次打开都有回到家的感觉。
13. 作为站主，我想在主页看到一道随机或最近的菜谱，以便在不知道吃什么的时候得到提示。
14. 作为站主，我想让主页在任何一个模块还没有数据时也能正常显示，以便新装的站不会一片报错。

### 理财 —— 预算

15. 作为站主，我想为某个月设置生活费预算总额，以便所有剩余额的计算有基准。
16. 作为站主，我想在月中修改当月预算，以便家里追加汇款或计划变化时数字仍然是真的。
17. 作为站主，我想让新的一个月自动沿用上个月的预算金额作为默认值，以便不用每月重复设置。

## Implementation Decisions

### 总体形态

- 单用户、自托管、公网可达。一个 Go 单体进程 + 一个 Postgres 实例，由 docker compose 编排在一台海外 VM 上。
- Go 1.25，HTTP 框架使用 **Echo v4**（路由、中间件、请求绑定与统一错误处理都走 Echo 的机制，不混用 `net/http` 原生 mux 或其他框架）。前端 React + TypeScript + Vite，构建产物通过 `embed.FS` 编入 Go 二进制。最终镜像只含一个可执行文件。
- 前端是 SPA + PWA（manifest + 图标 + 全屏显示模式）。**不实现 Service Worker 离线缓存与离线写入**。
- 货币固定为 RUB，金额一律以最小单位（копейка）存为 `bigint`，禁止浮点。
- 时区由配置项固定为站主所在地时区；数据库中所有时间戳存 UTC，「今天」「本月」等概念一律按配置时区计算。

### 模块边界（最重要的一条纪律）

代码分为三个业务模块与一个平台层：

- `finance`、`recipe`、`album` —— 三个业务模块，各自包含领域逻辑、数据访问与 HTTP 处理。
- `platform` —— 数据库连接、配置、认证、HTTP 中间件、图片处理与文件存储、时钟。

**任何业务模块不得引用另一个业务模块。** 需要共享的能力必须下沉到 `platform`。图片处理是这条纪律的第一个考验：菜谱和相册都要存图，因此「上传、生成缩略图、落盘、返回路径」的能力属于 `platform`，两个模块各自调用它并各自保存自己的元数据。

`main` 是唯一的装配处，手写依赖构造（`repo → service → handler` 三步 new），**不引入 DI 框架**。

### 模块内部的三层结构

每个业务模块内部固定分为 **handler / service / repo** 三层，各占一个包（例如 `internal/finance/handler`、`internal/finance/service`、`internal/finance/repo`）。依赖方向严格单向：`handler → service → repo`，反向引用与跨层跳跃（handler 直接调 repo）都不允许。

- **handler** —— 实现 `oapi-codegen` 为 Echo 生成的服务端接口。职责仅限：绑定与校验请求、把生成的 DTO 转换为领域类型、调用 service、把领域类型转换回 DTO、把领域错误映射为 HTTP 状态码。**不含任何业务规则，不直接触碰数据库。**
- **service** —— 模块的业务规则所在地：「今天可用」的计算、月末结算、大额开销写存款流水、「今天做了」的计数与日期更新等。依赖 repo **接口**（接口定义在 service 包中，由调用方拥有），依赖 `platform` 提供的时钟与文件存储。事务边界在这一层声明——需要多表写入的用例由 service 开启事务并把事务句柄传给 repo。
- **repo** —— 唯一写 SQL 的地方。每个模块的 repo 只访问自己的 schema。返回**模块内定义的领域结构体**，不返回 `database/sql` 的行对象，也不返回 OpenAPI 生成的类型。

**类型的流向**：repo 与 service 之间流动的是领域结构体；OpenAPI 生成的 DTO 只出现在 handler 层。这一层映射代码是刻意付出的成本——它换来的是业务层不被 API 契约绑死，契约变更不会穿透到业务规则。

repo 接口的存在同时是**测试缝**：service 层的单元测试用 fake repo 驱动，见「Testing Decisions」。除三个业务模块的 repo 接口外，仍然不引入其他抽象。

### 数据库

- 一个 database，四个 schema：`platform`、`finance`、`recipe`、`album`。schema 在数据库层面物理执行模块边界——跨模块外键在物理上不会出现。
- 迁移使用 goose，SQL 文件通过 `embed` 编入二进制，作为部署流程中的独立一步执行（`pull → migrate → up -d`），失败即中止，不切换应用版本。
- 数据访问按「正确使用 Postgres」的标准来：一切能表达的约束都写进 schema（`NOT NULL`、`CHECK`、外键、唯一索引），涉及多表写入的操作放在显式事务里，索引按实际查询模式建立。
- 照片 EXIF 使用 `jsonb`（厂商字段本身无固定 schema，这是恰当用法）。**不使用全文检索**：菜谱规模在两百条以内，`ILIKE` 足够。

#### `platform` schema

- `account` —— 单条记录：用户名、argon2id 密码哈希、创建与更新时间。
- `session` —— 会话令牌哈希、创建时间、过期时间、最后使用时间。会话通过 `HttpOnly; Secure; SameSite=Lax` cookie 传递，**不使用 JWT**。
- 登录失败限流在进程内存中实现（单实例部署，无需持久化）。

#### `finance` schema

- `category` —— 分类：名称、排序、是否归档。出厂预置一组常用分类（餐饮 / 日用 / 交通 / 固定 / 娱乐 / 学习 / 其他），可增删改与归档。归档只影响新记账时的可选项，历史账目仍正确显示分类名。
- `budget` —— 每个年月一条：预算金额（minor units）。创建新月份时默认沿用上一个月的金额。
- `expense` —— 一笔开销：发生日期、金额、分类、备注、**种类**。
  - 种类为三选一：`flexible`（弹性）、`fixed`（固定）、`large`（大额）。
  - `fixed` 与 `flexible` 一样计入当月预算消耗；它**不是**一个独立的周期性模板机制——站主在月初手动把预估值记为一条 `fixed` 开销，账单到达后直接编辑该笔开销的金额。这是刻意的简化：预扣是免费的，因为它不是新概念，只是提前记账。
  - `large` 不计入当月预算，改为在 `savings_ledger` 中生成一条等额的负向记录。
- `savings_ledger` —— 存款流水：发生日期、增减金额、原因（`month_settlement` / `large_expense` / `manual`）、可空的关联 `expense`、备注。**存款余额是这张表的求和**，不单独存一个可能失真的余额字段。
- `month_settlement` —— 已结束月份的不可变结算记录：年月、当时预算、实际支出、结余金额、结算时间。

#### `recipe` schema

- `recipe` —— 菜谱：名称、封面图信息、步骤（Markdown 文本）、成本估算（`estimated_cost`，即做这道菜大概花多少钱——**不叫「预算」**，「预算」一词在全站只指理财模块的月度生活费）、做过次数、上次做于、创建与更新时间。
- `ingredient` —— 食材：所属菜谱、名称、数量、单位、排序。
- `tag` 与 `recipe_tag` —— 多对多标签。

#### `album` schema

- `event` —— 事件：标题、开始日期、结束日期、正文（Markdown）、封面照片、创建与更新时间。
- `photo` —— 照片：所属事件、原图路径、预览图路径、缩略图路径、一句话说明、拍摄时间、EXIF（`jsonb`）、宽高、排序。

### 关键业务规则

- **本月已花** = 当月 `flexible` 与 `fixed` 开销之和。
- **本月剩余** = 当月预算 − 本月已花。可以为负；为负时前端显式提示超支。
- **今天可用** = 本月剩余 ÷ 本月剩余天数（含今天），向下取整。这是滚动式的：今天多花，明天自动变少；今天省下，明天自动变多。由于固定开销在月初就已记入，这个数字从每月 1 号起就是可信的。
- **大额开销**不参与上述任何计算，记录时同步写入一条负向存款流水。
- **月末结算**：当一个月份结束后，把该月的「本月剩余」（正或负）写入存款流水，并生成不可变的 `month_settlement` 记录。
  - **结算通过惰性触发实现，不引入调度器、cron 或后台队列**：任一 API 请求进入时检查是否存在已结束但未结算的月份，若有则在事务中补齐结算。这保证了单进程部署下的正确性，且不增加任何运维组件。

### 图片处理

- 上传后由 `platform` 在**请求内同步**处理：读取 EXIF、按方向校正、生成缩略图（约 400px）与预览图（约 1600px）、原图归档。**不引入消息队列或后台任务系统**——单张处理在百毫秒量级，一次上传二十张用一个加载态覆盖即可。
- 原图与派生图存放在 VM 文件系统的数据卷中，按模块与年月分目录。数据库只存路径与元数据。
- 图片通过应用自身的鉴权后再提供，不允许绕过登录直接访问静态目录。

### API 契约

- **Spec-first**：`api/openapi.yaml` 是唯一真相。
  - Go 端由 `oapi-codegen` 以 `echo-server` 为目标生成服务端接口、类型与参数校验中间件；各模块的 handler 层实现生成的接口，由编译器保证端点无遗漏。
  - TS 端由 `openapi-typescript` 生成类型、`openapi-fetch` 提供类型安全的调用。**不使用 openapi-generator。**
  - 生成产物提交进版本库；CI 中重新生成并比对，不一致即失败。
- 端点按模块分组：`/api/auth/*`、`/api/finance/*`、`/api/recipes/*`、`/api/album/*`。
- **每个业务模块各自暴露一个 `summary` 端点**，返回自己的一句话状态。据点主页的聚合发生在**前端**，后端不做跨模块联合查询——这是对模块边界的保护，也是主页设计的直接约束。
- 非 `/api` 前缀的路径一律交给内嵌的 SPA。

### 前端

- Vite + React + TypeScript，路由用 React Router，服务端状态用 TanStack Query，API 调用一律走生成的类型安全客户端。
- 设计令牌集中在一份 CSS 变量文件中，**组件内禁止出现硬编码颜色值**。视觉基调（配色、字体、间距、圆角、动效尺度）与世界观文档存放在 `docs/design/` 下，作为后续所有界面工作的参考。
- 提供一个仅站主可见的组件预览路由，用于集中调整视觉基调。

### 部署与 CI/CD

- 仓库为单体仓库（monorepo）：Go 后端、React 前端、OpenAPI 契约、迁移、部署编排、设计文档同处一仓。
- 任务运行器使用 `just`；前端包管理使用 `pnpm`；Go 静态检查使用 `golangci-lint`。
- 本地开发：docker compose 只跑 Postgres，Go 与 Vite 直接跑在宿主机以获得热重载。
- CI（GitHub Actions），`main` 分支触发：`go vet` + `golangci-lint` + `go test ./...`（含 repo 层与端到端测试，CI 中以 GitHub Actions 的 Postgres service 容器提供数据库）+ `tsc` + 前端构建 + 契约生成漂移检查 → 多阶段 Dockerfile 构建 → 推送镜像至 GHCR → 通过 SSH 在 VM 上执行 `pull → migrate → up -d`。任一步失败即中止，不部署。
- 依赖 Postgres 的测试用 build tag 或环境变量区分，本地可只跑不依赖数据库的 service / handler 层测试以获得秒级反馈，CI 上一律全跑。
- `dev` 分支只跑检查与测试，不部署。
- 提交前钩子只跑 `gofmt` 与 `tsc`，不跑测试。
- 生产环境前置 Cloudflare。

## Testing Decisions

### 什么是好测试

**测试是本项目的一等交付物，不是功能完成后的补充动作。** 每个里程碑的「完成」定义都包含测试；未被测试覆盖的行为视为未实现。

只测外部可观察的行为，不测实现细节——每一层的「外部」是它自己的契约（handler 的契约是 HTTP，service 的契约是它暴露的方法与领域类型，repo 的契约是它的接口方法）。测试应当在重构某一层内部实现时保持沉默，在改变该层契约或业务规则时失败。任何需要读懂实现才能读懂的测试都是坏测试。

### 四条测试缝

三层结构给出三条天然的缝，再加一条把它们串起来的端到端缝：

**1. repo 层 —— 真实 Postgres，不 mock 数据库。**

- 针对真实 Postgres 实例（testcontainers，或复用本地实例并为每条测试分配独立 database）执行全部 goose 迁移后运行。
- 断言 SQL 本身：写入后读回、筛选与排序条件正确、唯一约束与 `CHECK` 真的会拒绝坏数据、事务回滚后无残留。
- **绝不用 sqlmock 一类的伪数据库**——SQL 是最容易写错的部分，用假数据库测 SQL 等于什么都没测。

**2. service 层 —— fake repo，测业务规则。**

- 用手写的 fake repo（内存 map 实现 repo 接口，放在 service 包的测试文件里，**不引入 mock 生成框架**）驱动，配合可控时钟。
- 这是业务规则的主战场：「今天可用」的滚动行为、月末结算的幂等性、大额开销不计入月度预算而写入存款流水、分类归档的语义。这类规则用 fake repo 测起来又快又能穷举边界（超支、零预算、月末最后一天、跨月），不必为每个分支准备一整套数据库状态。
- fake repo 必须保持朴素：只做存取，不复刻 SQL 语义，**也不模拟事务与回滚**。事务边界虽然由 service 声明，但「多表写入是否真的原子」这件事只在 repo 层测试中对真实 Postgres 验证——不要为了在 service 层测事务而让 fake repo 长出事务语义。

**3. handler 层 —— fake service，测 HTTP 表层。**

- 用 Echo 的 `httptest` 配合 fake service 驱动，断言：请求绑定与参数校验、领域错误到 HTTP 状态码的映射（未找到 → 404、校验失败 → 400、未登录 → 401）、DTO 转换的正确性。
- 这一层的测试应当很薄。如果某个 handler 测试开始断言业务规则，说明业务规则漏进了 handler 层，应当下沉到 service。

**4. 端到端 —— 完整装配的应用 + 真实 Postgres，通过 HTTP 驱动。**

- 一个测试环境辅助包负责：启动 Postgres、执行全部 goose 迁移、装配完整应用、返回一个测试 HTTP 服务器与一个可控时钟。
- 测试使用由 OpenAPI 契约生成的类型来构造请求与解析响应，因此**契约本身也在被测试**。
- 这条缝**不追求分支覆盖**，只覆盖每个模块的主干路径与跨层协作：装配是否正确、认证中间件是否真的挂上了、事务是否真的提交了、序列化是否符合契约。边界与异常分支留给下面三层。

**分工原则**：一个行为只在它真正归属的那一层被详尽测试，其余层只测「有没有正确地把它接起来」。同一条业务规则不应在四条缝上被重复断言四遍。

### 注入点

`platform` 层提供两个可替换的接口：

1. **时钟** —— 「今天可用」「月末结算」「上次做于」全部依赖当前时间，测试必须能冻结与推进时间。
2. **文件存储根目录** —— 照片原图与派生图的落盘位置，测试中指向临时目录。

加上每层由**调用方**定义的窄接口（service 包定义它需要的 repo 接口，handler 包定义它需要的 service 接口，均由下层的具体类型隐式满足），这就是全部的抽象。接口一律定义在使用它的一侧、只列出真正用到的方法，**不在实现侧预先定义大而全的接口**，也不引入 mock 生成框架——fake 实现一律手写在测试文件里。

### 必须覆盖的行为

括号中标注该行为应当被详尽测试的那一层；端到端只跑其中的主干路径。

- 认证（service + 端到端）：未登录访问受保护端点被拒；登录成功后签发会话；会话过期后失效；登出使会话立即失效；连续失败触发限流。
- 理财 —— 业务规则（service）：本月剩余的计算；今天可用的滚动行为（推进时钟后数字随之变化）；固定开销计入预算而大额开销不计入；大额开销产生负向存款流水；月末结算在跨月后被惰性触发且只触发一次；超支月份从存款扣减。
- 理财 —— 数据访问（repo）：按月份与分类的筛选查询；存款余额的求和；结算记录写入与开销、存款流水写入处于同一事务；分类归档后历史账目仍显示正确分类名。
- 菜谱（repo 测查询与关联，service 测规则）：完整增删改查；「今天做了」使次数加一并更新上次做于；标签筛选；食材顺序。
- 相册（service 测编排，repo 测查询，端到端测上传）：事件增删改查；多图上传后生成缩略图与预览图且尺寸正确；EXIF 拍摄时间被提取并用于默认排序；未登录无法获取图片。
- HTTP 表层（handler）：每个模块至少覆盖一次参数校验失败 → 400、资源不存在 → 404、未登录 → 401 的映射。
- 迁移：repo 层与端到端测试环境每次从零执行全部迁移，迁移本身因此持续被验证。

### 前端

**刻意不建立前端测试缝。** React 层是「生成的类型安全客户端 + 展示」，单元测试收益极低。M0 引入**一个** Playwright 冒烟测试（登录 → 据点主页渲染 → 三个模块入口可达），此后不再扩展前端测试。

### 既有先例

无。代码库为全新项目，上述四条测试缝的脚手架（Postgres 测试环境辅助包、可控时钟、fake repo / fake service 的书写范式、Playwright 冒烟测试）属于本 spec 需要新建的内容，应在 M0 中随认证模块一并建立——认证模块本身就要走完 handler / service / repo 三层，因此它同时是三层结构与四条测试缝的参考实现，使 M1 起的每个功能都有现成的模板可抄。

CI 在每次 push 上运行全部后端测试（含需要 Postgres 的 repo 层与端到端测试），测试失败即中止流水线、不部署。

## Out of Scope

以下内容经过明确讨论后被否决，**不应在本 spec 范围内实现，也不应为其生成任务**：

- **备份、恢复与数据冗余** —— 本期不做。
- **消息队列、后台任务系统、任何形式的调度器** —— 图片处理同步完成，月末结算惰性触发。
- **离线记账与离线同步（含 CRDT、冲突解决）** —— PWA 不实现离线写入。
- **账单 OCR、小票识别、银行账户对接、账单 CSV 导入** —— 记账一律手动。
- **多币种与汇率** —— 固定 RUB。
- **跨月预算结转** —— 剩余进入存款，下个月预算重新开始。
- **份量换算（2 人份 → 4 人份）** —— 食材虽为结构化，但本期不实现换算。
- **存钱目标 / 讨伐目标** —— 存款本期只有余额与流水。
- **等级、经验值、成就、连续打卡等游戏化机制。**
- **跨模块聚合时间轴** —— 据点主页的聚合发生在前端，后端不做跨模块查询。
- **多用户、注册、找回密码、权限系统** —— 全站单用户。
- **JWT、OAuth、第三方登录、Passkey/WebAuthn。**
- **DI 框架**（依赖在 `main` 中手写装配）、**mock 生成框架**（fake 一律手写）、**独立于 handler/service/repo 之外的第四层**（不设 usecase 层、不设脱离 service 的纯 domain 层、不做 CQRS）。
- **Next.js / SSR / SEO 相关能力。**
- **openapi-generator。**
- **Postgres 全文检索、对象存储（原图存 VM 文件系统）、Kubernetes。**
- **性能优化与容量规划** —— 数据规模上限约为：照片一千张、菜谱两百道、开销记录每年数百条。任何针对更大规模的优化都是过度设计。

## Further Notes

- **领域语言以 `UBIQUITOUS_LANGUAGE.md` 为准**：该文档定义全部领域术语与其**代码标识符**（数据库列名、Go 类型与字段、OpenAPI schema 名一律采用）。本 spec 与它冲突时以它为准。已定案的几条易错项：开销的实体名是 `expense`（不是 `entry`）；菜谱的花费叫**成本估算** `estimated_cost`（「预算」只指理财的月度生活费）；进行中的月份说**本月剩余**、已结算的月份说**结余**；「今天可用」不叫「每日预算」。
- **命名待定**：本 spec 与领域语言文档均使用中性命名（「理财模块」「相册」「据点主页」「存款」）。世界观与日文命名表（例如《収支の記録》《料理魔導書》《記憶の結晶》，存款可显示为「貯金」）将在一场独立的对话中确定——它是叠在领域语言之上的**展示层**，只替换用户可见文案，**不改动概念划分与代码标识符**。实现时请把用户可见文案集中放置，以降低这次替换的成本。
- **不使用任何受版权保护的素材**：主题灵感来自日式异世界作品，但站内不得使用任何原作的插画、角色、logo 或字体资产。视觉效果一律由 CSS 与自由许可字体实现。
- **两个学习目标是刻意保留的非最优选择**：以本项目的数据规模，Postgres 相对于 SQLite 没有技术收益，选择它是为了扎实学会正确使用 Postgres；完整的 CI/CD 链路同理。这两项被限定在「用对」而非「炫技」的范围内——不做为了练手而制造的合成负载、性能实验或多余的基础设施。所有其他技术决策一律取最简方案。
- **第一目标始终是「这个站我每天都会用」**。当工程优雅与使用频率冲突时，使用频率优先。记账流程的速度（金额 → 分类 → 完成）是理财模块的生死线，任何增加记账摩擦的设计都应当被拒绝。
