## OQ-1｜四个模块的 handler 如何共同满足一个 `ServerInterface`

**挡在：** M0（认证是第一个真正的模块，写它的时候就必须回答）

**含糊在哪：** `oapi-codegen` 生成的是**一个**接口，而实现分散在四个模块（`auth` / `finance` / `recipe` / `album`）的 handler 包里。谁来把它们拼成一个值传给 `RegisterHandlersWithBaseURL`？

底下还埋着一个**导入环**：模块 handler 要用 `internal/api` 的 DTO，所以 `finance/handler → internal/api`。如果组合体也放在 `internal/api` 里，就是 `internal/api → finance/handler`，环成立、编译不过。

**岔路：**
- 组合结构体放在 `cmd/vellum`——装配处本来就唯一，多装配一个结构体是同一件事的延伸。
- 新开一个 `internal/httpapi` 专门放组合体。
- 不组合：每个模块自己 `RegisterHandlers` 一部分——但生成的接口是整体的，做不到。

**倾向：** `cmd/vellum`。顺带要决定现在 `internal/api/handler.go` 里的健康检查搬去哪——它不属于任何业务模块。

**定案后写进：** `architecture.md` 的「契约管线」（那里现在标着「（待定）」）。

## OQ-2｜事务句柄怎么从 service 传到 repo

**挡在：** M0（认证模块就是所有模块要抄的模板，这条定错了要改三遍）

**含糊在哪：** 已经定的是「事务边界在 service 层声明、句柄传给 repo」。但**句柄长什么样**没定，而它直接决定 repo 接口的形状，进而决定 fake repo 怎么写。

**岔路：**
- `repo.WithTx(tx) Repo`——返回一个绑定了事务的新 repo。接口干净，但每个 repo 要写一份 `WithTx`。
- 每个 repo 方法多一个 `pgx.Tx` 参数——最直白，但非事务调用要传什么？
- service 只见 `Querier` 接口（`*pgxpool.Pool` 与 `pgx.Tx` 都满足），事务由一个 `txManager` 包起来——最干净，但它是一个额外的抽象，和「除 repo 接口外不引入其他抽象」有张力。

**还要一并回答：** fake repo 不模拟事务，那 service 接口上的「开启事务」这一步在 fake 里返回什么？（可能的答案：让 fake 的 `WithTx` 返回它自己。）

**定案后写进：** `architecture.md` 的「业务模块的三层」。

## OQ-3｜领域错误怎么表达

**挡在：** M0

**含糊在哪：** handler 要把「未找到」映射成 404、「校验失败」映射成 400。但「未找到」这个错误值长什么样没定。现有纪律说「接口一律定义在使用方」，可错误类型不是接口，这条纪律没覆盖它。

**岔路：**
- 每个模块自己定 sentinel error（`finance.ErrNotFound`），handler 用 `errors.Is` 判断——不引入共享，但四个模块会长出四套几乎相同的写法。
- `platform` 提供一组通用错误类型（`NotFound` / `Conflict` / `Invalid`），各模块包装自己的信息——共享了，但 `platform` 里多一个所有模块都依赖的东西。
- 让 service 直接返回 `*echo.HTTPError`——最省事，也最错：业务层从此被 HTTP 绑死。

**倾向：** 第二种。这正是「需要共享的能力下沉到 `platform`」的正当用法。

**定案后写进：** `architecture.md`——「结构 · 每个业务模块三层」（handler 层职责），如果它成为一条纪律则同时进「纪律」。

## OQ-4｜30 天登录态与「GET 不得有副作用」的冲突

**挡在：** M0

**含糊在哪：** `platform.session` 有 `last_used_at`。如果每次请求都更新它，那**每一个 GET 都在写库**——而 `architecture.md` 的「GET 不得有副作用」只给惰性结算开了一个口子，没给这个。这条冲突现在文档里是漏的。

**要一并回答的是：**
1. 「保持登录约 30 天」是**登录起算固定 30 天**（到期就重新输密码），还是**滑动续期**（每次使用往后推）？固定就完全不需要写库。
2. 如果要写，是每次都写，还是「距上次更新超过某个阈值才写」（比如 1 天）？
3. `last_used_at` 到底要用来干什么？如果只是「想知道上次什么时候用的」，它可能根本不值得这个代价。

**倾向：** 固定 30 天 + `last_used_at` 降级为「每天最多写一次」，或者直接从表里去掉。单用户站点没有「查看我的活跃会话」这种需求。

**定案后写进：** `data-model.md`（`session` 表）+ `architecture.md` 的「GET 不得有副作用」（如果需要第二个例外，必须在那里论证为什么它没有攻击面）。

## OQ-5｜改动一笔已结算月份的开销会怎样

**挡在：** M1。**这是产品决策，需要站主拍板，不是工程问题。**

**含糊在哪：** `month_settlement` 是不可变的，存款余额是流水求和。但站主可以编辑任何一笔开销（需求 29）、也可以把日期改到过去（需求 24）。于是：把一笔 3 月的开销日期改成 2 月（2 月已结算），或直接改一笔 2 月开销的金额——那条不可变记录就和事实对不上了，存款余额也跟着失真。

**岔路：**
- **禁止**：已结算月份的开销不可编辑、不可删除，也不能把开销的日期改到已结算的月份。最简单，账面永远自洽，代价是补记账有个硬期限。
- **允许但不重算**：承认结算记录是「结算那一刻的快照」，事后改动不回溯。存款余额会与「按当前账目重算」的结果不一致——需要接受这一点。
- **允许并重算**：改动触发受影响月份的重新结算，存款流水随之更新。最诚实，也最复杂（可能要连锁重算多个月）。

**倾向：** 第一种。这个站的记账窗口是「当天或前几天」，一个已经过完并结算了的月份被翻出来改的概率极低，为它引入重算机制不划算。但这取决于站主实际会不会补很久以前的账。

**定案后写进：** `PRD.md` 的业务规则 + `data-model.md`。

## OQ-6｜惰性结算挂在哪一层

**挡在：** M1

**含糊在哪：** 说的是「任一 API 请求进入时检查是否有已结束但未结算的月份」。四个子问题都没答：

1. **挂在哪？** 中间件属于 `platform`，结算规则属于 `finance`，而 `platform` 不能 import `finance`。可行的做法是在 `cmd/vellum` 里把 finance 的结算函数注入给 platform 的中间件——**这是模块边界纪律的第二个考验**（第一个是图片处理），值得像那个一样写进 `architecture.md`。
2. **多个月怎么办？** 连续三个月没打开站，要能循环补齐。
3. **幂等靠什么？** `month_settlement(year_month)` 上的唯一索引 + `ON CONFLICT DO NOTHING`？还是 advisory lock？
4. **每个请求都跑一次 `SELECT` 值不值？** 单实例部署，可以用一个内存里的「已确认结算到哪个月」把绝大多数请求短路掉——但这就引入了一处需要小心的进程内状态。

**定案后写进：** `architecture.md`（挂载点与边界）+ `data-model.md`（幂等约束）。

## OQ-7｜大额开销与存款流水的联动缺口

**挡在：** M1。**部分是产品决策。**

**含糊在哪：** 已定的只有「创建 `large` 时写一条负向流水」。没定的是：

- **编辑 `large` 的金额** → 关联流水要同步改？还是追加一条差额流水？
- **改种类**（`flexible` → `large`，或反过来）→ 种类到底可不可变？如果可变，要生成或撤销流水。
- **删除 `large`** → 关联流水删掉，还是写一条正向冲抵？

存款余额是流水求和，任何一条漏了它就不再诚实——而「存款余额必须是一个诚实的数字」是站主自己定下的原则。

**倾向：** 金额与删除都直接改/删关联流水（`savings_ledger` 已经有一个可空的 `expense` 外键，就是为这个准备的）；种类**允许**变更，因为记账时点错种类是很常见的。

**定案后写进：** `PRD.md` 的业务规则 + `data-model.md`。

## OQ-8｜图片怎么在鉴权之后提供

**挡在：** M3（菜谱封面是第一次需要它），但**契约的形状要更早定**。

**含糊在哪：** 已定的是「图片通过应用自身的鉴权后再提供，不允许绕过登录直接访问静态目录」。没定的是怎么做：

- **路径挂哪？** 非 `/api` 前缀的路径一律交给 SPA，所以图片要么挂在 `/api` 下，要么另开一个前缀并在 SPA 路由里排除它。
- **怎么发？** Go handler 直接流出文件最简单，但要自己处理 `Range`、`ETag` 与缓存头，否则相册在手机上会很难受。
- **契约要不要描述它？** OpenAPI 描述二进制响应是可以的，但生成的类型对 `<img src>` 这种用法没有意义——也许它根本不该进契约。
- **孤儿文件谁清理？** `platform` 存图但不建表，两个模块各存各的路径。删除一张照片后，磁盘上那三个文件（原图 / 预览 / 缩略）现在没有任何人负责删。

**定案后写进：** `architecture.md`（platform 的图片能力）+ `data-model.md`（孤儿文件的责任归属）。

## OQ-9｜测试用哪一套 Postgres

**挡在：** M0（测试脚手架是 M0 的交付物）

**含糊在哪：** 最初的 spec 同时提了三种，它们是三套方案：

- testcontainers（本地与 CI 同一条路径，代价是每次跑测试都要拉/起容器）
- 复用本地已有实例，为每条测试分配独立 database（最快，但依赖「本地有个跑着的 Postgres」）
- CI 用 GitHub Actions 的 Postgres service 容器（CI 侧最省事，但本地和 CI 就成了两条路径）

**倾向：** 收敛成一套，本地与 CI 走同一条路径。两条路径意味着「本地全绿、CI 全红」这类问题会周期性出现。

**定案后写进：** `testing.md` 的第 1 条缝。

## OQ-11｜部署流水线的四个空白

**挡在：** M0

**含糊在哪：** `pull → migrate → up -d` 这三步之外，还有四件事没定：

## OQ-12｜`budget` 行何时创建

**挡在：** M1

**含糊在哪：** 「新月份自动沿用上个月的预算金额」有两种实现，行为不同：

- **惰性插入一行**——那又是一个有副作用的 GET，要么并进 OQ-6 的结算流程里（它本来就是每月一次的动作），要么再论证一次。
- **查询时 fallback 到上月**——不写库，但「月中修改当月预算」就得先 `INSERT` 再 `UPDATE`，而且「这个月的预算是继承来的还是我设的」这个区别在库里消失了。

**还要回答：** 当月完全没有预算（比如第一次使用）时，今天可用返回什么——`null`、`0`，还是前端根本不显示这张卡片？需求 14 说「任何一个模块还没有数据时主页也要能正常显示」，所以这个答案必须存在。

**定案后写进：** `PRD.md` 的业务规则 + `data-model.md`。

## OQ-13｜分类到底能不能删除

**挡在：** M1。**这是一个文档缺陷，不是设计难题。**

**含糊在哪：** 三处说法不一致：

- `PRD.md` 的需求 33–36 只有新增、重命名、归档，**没有删除**。
- `UBIQUITOUS_LANGUAGE.md` 的「分类」写的是「可增删改与归档」。
- 最初的 spec 也写的是「可增删改与归档」。

而 `expense` 有外键指向 `category`，删掉一个被引用的分类，历史账目就崩了——这正是「归档」这个概念存在的理由。

**倾向：** 「有开销引用时只能归档，从未被引用过的分类可以删除」，并把 UL 那句话改掉。也可以更简单：**只能归档，不能删除**。

**定案后写进：** `UBIQUITOUS_LANGUAGE.md`（改掉那句话）+ `data-model.md`（外键的 `ON DELETE` 行为）。

## OQ-14｜JSON 里的金额用什么类型

**挡在：** M1

**含糊在哪：** 金额在库里是 `bigint`。OpenAPI 里写 `type: integer, format: int64` 的话，`openapi-typescript` 会生成 `number`——JS 的 `number` 只能安全表示到 2⁵³。

本项目的量级完全安全（月预算 5 万卢布 = 5,000,000 копеек，差着九个数量级），**所以答案很可能就是 `number`**。但这条要显式写下来并说明为什么安全，否则将来任何人看到 `bigint` 对 `number` 都会停下来想半天，或者「顺手修复」成 string。

**定案后写进：** `architecture.md` 的「纪律 · 金额」。
