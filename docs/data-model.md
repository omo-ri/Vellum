# 数据模型

这份文档回答的是**「库里有哪些表、每张表为什么长这样」**。

概念之间的关系（一个事件有几张照片）看 [`UBIQUITOUS_LANGUAGE.md`](../UBIQUITOUS_LANGUAGE.md) 的 Relationships；表放在哪个包访问、事务在哪一层开看 [`architecture.md`](architecture.md)。列的确切类型与约束以 `migrations/` 下的 SQL 为准——**这份文档描述意图，迁移文件是事实**。

标注 **（未落地）** 的表是已经定案、但还没有迁移文件的。

## 全局约定

- **全部表放在默认 schema，不分 schema。** 下面的小节只是按模块分组，不对应数据库对象。曾经打算用 schema 让模块边界成为物理事实，但 Postgres 本来就允许跨 schema 外键——它并没有真的挡住什么，只增加迁移与连接配置的麻烦（理由见 [`architecture.md`](architecture.md) 的「不做什么」）。**跨模块外键不写**，这条靠纪律。
- **一切能表达的约束都写进 schema**：`NOT NULL`、`CHECK`、外键、唯一索引。约束写在库里，应用代码就不必自觉。
- **时间一律 `timestamptz` 存 UTC**，「今天」「本月」按 `SITE_TIMEZONE` 计算。
- **金额一律 RUB 最小单位（копейка）存 `bigint`**，禁止浮点。
- 索引按实际查询模式建立，不预先撒。数据规模上限见 [`architecture.md`](architecture.md) 的「明确不引入」。

## `auth`

站主的身份与会话。`auth` 是业务模块——有端点、有规则、有自己的表，因此照常三层；`platform` 那边只有密码哈希与会话中间件两样横切能力（见 [`architecture.md`](architecture.md) 的「平台层」）。

| 表 | 内容 | 值得注意的约束 |
| --- | --- | --- |
| `account` | 站主：用户名、argon2id 密码哈希、创建与更新时间 | `account_singleton` 是一个建在常量表达式 `(true)` 上的唯一索引——每一行都产出同一个键，第二行插入必然冲突。「单用户站点最多一行」因此由数据库强制 |
| `session` | 会话令牌哈希、创建时间、过期时间、最后使用时间 | 存哈希不存原值。会话通过 `HttpOnly; Secure; SameSite=Lax` cookie 传递 |

登录失败限流**不建表**，在进程内存中实现——单实例部署，重启后清空是可以接受的。

## `finance`（未落地）

| 表 | 内容 |
| --- | --- |
| `category` | 分类：名称、排序、是否归档。出厂预置一组常用分类（餐饮 / 日用 / 交通 / 固定 / 娱乐 / 学习 / 其他）。归档只影响新记账时的可选项，历史开销仍正确显示分类名 |
| `budget` | 每个年月一条：预算金额（minor units）。创建新月份时默认沿用上一个月的金额 |
| `expense` | 一笔开销：发生日期、金额、分类、备注、种类 |
| `savings_ledger` | 存款流水：发生日期、增减金额、原因、可空的关联 `expense`、备注 |
| `month_settlement` | 已结束月份的不可变结算记录：年月、当时预算、实际支出、结余金额、结算时间 |

三处设计要点：

- **`expense.kind` 是三选一**（`flexible` / `fixed` / `large`），用 `CHECK` 约束而不是单独一张类型表——它是一个封闭的、由代码逻辑消费的枚举，不是用户可维护的数据。`fixed` 与 `flexible` 在所有计算里完全等价，差别只在语义；`large` 不计入当月预算。
- **存款余额是 `savings_ledger` 的求和，不单独存字段。** 一个余额字段有两个来源就必然会失真；求和只有一个来源，永远诚实。这张表的规模（每年几十条）让求和的代价可以忽略。`savings_ledger` 上那个可空的 `expense` 外键是为大额开销准备的——但「编辑或删除一笔大额开销时流水怎么跟着动」尚未定案，见 OQ-7。
- **`month_settlement` 写入后不可变。** 它冻结的是那一刻的事实，不是一个可以随账目变化而重算的视图。「改动一笔已结算月份的开销会怎样」尚未定案，见 [`open-questions.md`](open-questions.md) 的 OQ-5。

## `recipe`（未落地）

| 表 | 内容 |
| --- | --- |
| `recipe` | 菜谱：名称、封面图信息、步骤（Markdown 文本）、成本估算、做过次数、上次做于、创建与更新时间 |
| `ingredient` | 食材：所属菜谱、名称、数量、单位、排序 |
| `tag` / `recipe_tag` | 多对多标签 |

- 成本估算的列名是 `estimated_cost`，**不叫 budget**——「预算」一词在全站只指理财的月度生活费。
- 做过次数与上次做于是**冗余存储的派生值**（可以由一张烹饪记录表求出）。这里刻意不建那张表：站主要的只是这两个数字，不是烹饪史。
- 步骤是一整块 Markdown 文本，不做结构化拆分——写菜谱时不该被表单结构限制。

## `album`（未落地）

| 表 | 内容 |
| --- | --- |
| `event` | 事件：标题、开始日期、结束日期、正文（Markdown）、封面照片、创建与更新时间 |
| `photo` | 照片：所属事件、原图路径、预览图路径、缩略图路径、说明、拍摄时间、EXIF（`jsonb`）、宽高、排序 |

- **EXIF 用 `jsonb`**：厂商字段本身没有固定 schema，这是 `jsonb` 恰当的用法之一，不是偷懒。
- **数据库只存路径，文件在磁盘上。** 派生图的生成与落盘由 `platform` 负责，两个模块各自保存自己的元数据。孤儿文件的清理责任尚未定案，见 OQ-8。
- `event.cover` 必须是该事件自己的照片之一，这条由外键 + 应用层校验共同保证。

## 不做全文检索

菜谱规模在两百条以内，按名字搜索用 `ILIKE` 足够。引入 `tsvector`、触发器与 GIN 索引会带来三份需要长期维护的东西，换来的是在这个数据量上测不出差别的性能。
