# 测试

这份文档回答的是**「一个行为应该在哪一层被测、用什么驱动」**。

分层结构本身看 [`architecture.md`](architecture.md)。

> **测试是本项目的一等交付物，不是功能完成后的补充动作。** 每个里程碑的「完成」定义都包含测试；未被测试覆盖的行为视为未实现。

## 什么算好测试

**只测外部可观察的行为，不测实现细节**——每一层的「外部」是它自己的契约：handler 的契约是 HTTP，service 的契约是它暴露的方法与领域类型，repo 的契约是它的接口方法。

测试应当在重构某一层内部实现时保持沉默，在改变该层契约或业务规则时失败。**任何需要读懂实现才能读懂的测试都是坏测试。**

## 四条缝

三层结构给出三条天然的缝，再加一条把它们串起来的端到端缝。

### 1. repo —— 真实 Postgres

- 针对真实 Postgres 实例，执行全部 goose 迁移后运行。
- 断言 SQL 本身：写入后读回、筛选与排序条件正确、唯一约束与 `CHECK` 真的会拒绝坏数据、事务回滚后无残留。
- **绝不用 sqlmock 一类的伪数据库。** SQL 是最容易写错的部分，用假数据库测 SQL 等于什么都没测——它只能证明「我拼出了我以为我要拼的字符串」。

### 2. service —— fake repo + 可控时钟

- 用**手写**的 fake repo（内存 map 实现 repo 接口，放在 service 包的测试文件里）驱动，配合可控时钟。不引入 mock 生成框架。
- 这是业务规则的主战场：今天可用的滚动行为、月末结算的幂等性、大额开销不计入月度预算而写入存款流水、分类归档的语义。这类规则用 fake repo 测起来又快又能穷举边界（超支、零预算、月末最后一天、跨月），不必为每个分支准备一整套数据库状态。
- **fake repo 必须保持朴素**：只做存取，不复刻 SQL 语义，**也不模拟事务与回滚**。事务边界虽然由 service 声明，但「多表写入是否真的原子」只在 repo 层对真实 Postgres 验证——不要为了在 service 层测事务而让 fake repo 长出事务语义。

### 3. handler —— fake service

- 用 Echo 的 `httptest` 配合 fake service 驱动，断言：请求绑定与参数校验、领域错误到 HTTP 状态码的映射、DTO 转换的正确性。
- **这一层的测试应当很薄。** 如果某个 handler 测试开始断言业务规则，说明业务规则漏进了 handler 层，应当下沉到 service。

### 4. 端到端 —— 完整装配 + 真实 Postgres，走 HTTP

- 一个测试环境辅助包负责：启动 Postgres、执行全部 goose 迁移、装配完整应用、返回一个测试 HTTP 服务器与一个可控时钟。
- 测试使用由 OpenAPI 契约生成的类型来构造请求与解析响应，因此**契约本身也在被测试**。
- 这条缝**不追求分支覆盖**，只覆盖每个模块的主干路径与跨层协作：装配是否正确、认证中间件是否真的挂上了、事务是否真的提交了、序列化是否符合契约。边界与异常分支留给上面三层。

### 分工原则

**一个行为只在它真正归属的那一层被详尽测试，其余层只测「有没有正确地把它接起来」。** 同一条业务规则不应在四条缝上被重复断言四遍——那样改一次规则要改四处测试，测试就从资产变成了负债。

## 注入点

`platform` 只提供两个可替换的东西：

1. **时钟** —— 今天可用、月末结算、上次做于全部依赖当前时间，测试必须能冻结与推进时间。业务代码因此**不得直接调 `time.Now()`**（这条纪律记在 [`architecture.md`](architecture.md) 的「纪律 · 时间」）。
2. **文件存储根目录** —— 照片原图与派生图的落盘位置，测试中指向临时目录。

加上每层由**调用方**定义的窄接口（service 包定义它需要的 repo 接口，handler 包定义它需要的 service 接口），这就是全部的抽象。

## 必须覆盖的行为

括号中标注该行为应当被**详尽**测试的那一层；端到端只跑其中的主干路径。

| 领域 | 行为 |
| --- | --- |
| 认证（service + 端到端） | 未登录访问受保护端点被拒；登录成功后签发会话；会话过期后失效；登出使会话立即失效；连续失败触发限流 |
| 理财 · 业务规则（service） | 本月剩余的计算；今天可用的滚动行为（推进时钟后数字随之变化）；固定开销计入预算而大额开销不计入；大额开销产生负向存款流水；月末结算在跨月后被惰性触发**且只触发一次**；超支月份从存款扣减 |
| 理财 · 数据访问（repo） | 按月份与分类的筛选查询；存款余额的求和；结算记录写入与开销、存款流水写入处于同一事务；分类归档后历史账目仍显示正确分类名 |
| 菜谱（repo 测查询与关联，service 测规则） | 完整增删改查；「今天做了」使次数加一并更新上次做于；标签筛选；食材顺序 |
| 相册（service 测编排，repo 测查询，端到端测上传） | 事件增删改查；多图上传后生成缩略图与预览图且尺寸正确；EXIF 拍摄时间被提取并用于默认排序；未登录无法获取图片 |
| HTTP 表层（handler） | 每个模块至少覆盖一次：参数校验失败 → 400、资源不存在 → 404、未登录 → 401 |
| 迁移 | 不单独写测试——repo 层与端到端测试环境每次从零执行全部迁移，迁移因此持续被验证 |

## 前端

**刻意不建立前端测试缝。** React 层是「生成的类型安全客户端 + 展示」，单元测试收益极低。

M0 引入**一个** Playwright 冒烟测试（登录 → 据点主页渲染 → 三个模块入口可达），此后不再扩展。

## 参考实现

认证模块本身要走完 handler / service / repo 三层，因此它同时是三层结构与四条测试缝的**参考实现**——脚手架（Postgres 测试环境辅助包、可控时钟、fake repo / fake service 的书写范式、Playwright 冒烟测试）在 M0 随它一并建立，使 M1 起的每个功能都有现成的模板可抄。

CI 在每次 push 上运行全部后端测试（含需要 Postgres 的 repo 层与端到端测试），测试失败即中止流水线、不部署。
